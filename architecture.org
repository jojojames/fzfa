* About this file

Canonical reference for *how fzfa works today*.

This file describes /implemented/ behavior only. Speculative redesigns
and "this would be nice" notes belong in =project.org=, not here. When
the implementation changes, update this file in the same commit.

Sibling architecture docs (read together):

- [[https://github.com/dangduc/fzf-native/blob/HEAD/architecture.org][fzf-native/architecture.org]]
  — the C module under us. Read this for
  thread/lock/arena/scoring internals.
- [[https://github.com/jojojames/fussy/blob/HEAD/architecture.org][fussy/architecture.org]]
  — the completion-style framework next to us. fzfa deliberately
  routes *around* fussy via its own completion category.

* Place in the pipeline

fzfa is the Elisp-side =completing-read= experience built on top
of =fzf-native='s sync and async surfaces. It owns the user-visible
plumbing — completion style, frontend integration, prompt overlay,
timers, and a set of convenience commands.

#+begin_src
  ┌──────────────────────┐    ┌──────────────────────┐
  │ fzfa-           │    │ fzf-sync-            │
  │ completing-read      │    │ completing-read      │
  │ (streaming child)    │    │ (in-memory list)     │
  └──────────┬───────────┘    └──────────┬───────────┘
             │                           │
             │ fzf-native-async-*        │ fzf-native-score-all
             ▼                           ▼
  ╔════════════════════════════════════════════════════╗
  ║ fzf-native (C dynamic module)                      ║
  ║   reader thread + scoring thread + counting sort   ║
  ╚════════════════════════════════════════════════════╝
#+end_src

The interesting performance work is in =fzf-native=. The interesting
UX work is right here.

* The two completing-read entry points

| Entry point                  | Backend call                      | Use when                                          |
|------------------------------+-----------------------------------+---------------------------------------------------|
| =fzfa-async-completing-read=  | =fzf-native-async-*= (streaming)  | Candidates come from a long-running shell command (=find=, =rg=, =git ls-files=, etc.). |
| =fzfa-sync-completing-read=   | =fzf-native-score-all= (sync batch) | Candidates are an already-realized Elisp list and you just want fzf scoring + ordering. |

Both wrap =completing-read=, register the =fzfa= completion
category, and reuse the same passthrough completion style.

* Async pipeline — =fzfa-async-completing-read=

#+begin_src
  completion table(query)
    key = (query, limit, case-mode, fuzzy,
           filter-only-length, filter-only-logic)
    if key changed:
      clear old local ownership
      request-id = fzf-native-async-submit(handle, query, limit)
    status = fzf-native-async-status(handle, request-id)
    if status failed:
      retain and report one terminal error for this key
    else if no usable result belongs to this request:
      keep the prior displayed result
    else if snapshot-generation or presentation changed:
      snapshot = fzf-native-async-snapshot(handle, request-id)
      recheck snapshot identity and local request ownership
      request-output = (final/partial candidates filtered total)
    return request-output

  regular timer (50 ms)
    poll status :snapshot-generation without copying candidates
    on change, schedule an idle-timer frontend exhibit
#+end_src

The request key lives in =fzfa-source=.  One changed key creates one native
request, and every later status or snapshot names that request ID.  A submit or
matcher failure is a terminal value for that key rather than work that redraw
can silently retry.  Producer failure is reported independently, because a
producer can fail after emitting a useful partial candidate set.

The child producer, native reader, scoring coordinator, and process-wide
workers run outside Elisp.  Elisp runs on its main thread and never waits for
scoring.  =fzf-native-async-status= copies only metadata.  Candidate strings
cross the module boundary through =fzf-native-async-snapshot=.  Each usable
generation requires one copy per presentation policy.  The completion table
retains that output for stable redraws.

The native =:stale= flag covers both an older query and a growing candidate
pool.  When a nonempty partial result belongs to the current request, fzfa
accepts it.  Thus, candidates can appear before the producer finishes.
The candidate list and counts come from the same snapshot.  An empty partial
result remains pending.  Only a complete, non-stale result can clear the display
with zero matches.

Snapshot construction can call Lisp hooks, so the handle and
request epoch must still belong to the source before publication.  A hook can
also yield to a nested render of the same request.  If that render changes the
cached output, the outer render returns interrupted and preserves the nested
publication.  This covers newer generations, same-generation presentation
changes, and terminal errors; generation comparison alone does not.  The
presentation key is captured before snapshot construction so it describes the
policy that built the strings.

Fzfa requires fzf-native 2.7.  Shell-command sources use the POSIX session API
supplied by that release.  The Windows module provides batch scoring only, so
static and callback-based =:candidates= sources remain available there while
=:command= sources stop with a user-facing error.

For the C-side mechanics — what =score_abort= does, how the same-
filter rule prevents livelock, how the arena handles teardown — see
=fzf-native/architecture.org=.

** Result cache (C-side)

Each native session maintains an LRU result cache keyed by the complete matcher
identity.  Its entry count is configured by =fzfa-cache-size= (default 40,
read at session start); fzf-native also enforces its own byte budget.  An entry
stores top-K output and, when the byte budget permits, membership evidence for
refining a later request.

On every dispatch, the C side classifies the lookup:

| Outcome     | When                                          | Effect                                          |
|-------------+-----------------------------------------------+-------------------------------------------------|
| Exact-fresh | Same matcher identity, pool unchanged         | Publish cached top-K; no scoring scheduled.     |
| Exact-stale | Same matcher identity, pool has grown         | Reuse membership and score the appended delta.  |
| Refinement  | New query safely subsumes a cached query      | Score prior members plus the appended delta.    |
| Miss        | No safe cache evidence                        | Scan the selected pool boundary.                 |

The refinement path is what makes incremental typing fast: typing =foo= after
=fo= can rescore only candidates that matched =fo= plus later arrivals.
Subsumption uses byte-prefix and parsed-term-set checks; unsafe forms fall back
to a full scan.  Membership evidence is an optimization only.  Dropping it for
the byte budget must not change result order or counts.

For LRU details, =SharedIdx= refcounting, the subsumption rule, and
the parsed-pattern caching, see =fzf-native/architecture.org= §
"Result cache".

* Sync pipeline — =fzfa-sync-completing-read=

When the candidate list is already an in-memory Elisp list (e.g. SSH
host names from =~/.ssh/config=, or buffer names), there is no value
in spinning up a child process. =fzfa-sync-completing-read= is the
direct path:

#+begin_src
  user types "fo"
       │
       ▼
  ┌──────────────────────────────────────────────────┐
  │ Elisp: completion table lambda                   │
  │  - reads minibuffer query                        │
  │  - empty query? → return candidates unchanged    │
  │  - else: (fzf-native-score-all candidates query) │
  │  - returns scored, sorted vector                 │
  └──────────────────────────────────────────────────┘
       │
       ▼
  frontend (vertico/icomplete) renders
#+end_src

No timers, no overlay refresh, no abort plumbing. Each keystroke
re-scores the entire list synchronously. =fzf-native-score-all= is
parallelized internally (see =fzf-native/architecture.org=), so this
remains snappy for tens of thousands of candidates.

* Multi-source — =fzfa-multi-read= and =fzfa-find-any=

A multi-source command merges several "sources" (each backed by either a
sync candidate list or an async shell command) into one
=completing-read=, with grouped, fzf-scored results.  Top-of-group fzf
score determines per-tick group order; ties fall back to declared source
order via =sort='s stability.

#+begin_src
  ┌────────────────────────────────────────────────────────────────────┐
  │ fzfa--multi-read (orchestrator)                               │
  │   • per-source structs: handle, request ID/key/output,              │
  │     last result, rank, totals, filtered, last generation            │
  │   • shared timer polls async snapshot generations                  │
  │   • collection lambda's 't action:                                 │
  │       for each source:                                             │
  │         async → fzfa--source-async-out (submit/status/snapshot)   │
  │         sync  → (fzf-native-score-all items query)                 │
  │       pending/failed → preserve last result                        │
  │       final → update result, rank, filtered, total                 │
  │       sort sources by rank (stable → declared order on tie)        │
  │       concat last-results in sorted order                          │
  │   • affixation-function pads candidates to a uniform column        │
  │     before appending each source's :annotate output                │
  │   • group-function reads source via fzfa-src-idx text-prop    │
  │     and returns the source :name                                   │
  │   • on selection: source's :action is funcalled with the cand      │
  └────────────────────────────────────────────────────────────────────┘
#+end_src

** Source derivation: extract / inject

Sources are not duplicated as parallel data structures.  Every existing
single-source command (e.g. =fzfa-buffer=, =fzfa-spotlight-apps=)
is the source of truth; =fzfa-multi-read= replays each
command twice per session to obtain a source plist:

1. *Extract* — a dynamic var =fzfa--multi-mode= is bound to
   =:extract=, and the command is funcalled.  Inside
   =fzfa-async-completing-read= / =fzfa-sync-completing-read=, the entry
   point sees the flag and =throw='s the keyword args (=:prompt=,
   =:command= or =:items=, =:directory=, =:category=, =:annotate=).
   The command's =when-let*= fails to bind, post-action never runs.
2. *Inject* — after the user picks =CAND=, =fzfa--multi-mode= is
   bound to =(:inject . CAND)=, and the command is funcalled again.
   The completing-read entry point sees the flag and returns =CAND=
   directly.  The =when-let*= binds, and the post-action (e.g.
   =(switch-to-buffer result)=) runs.

#+begin_src
  USER: M-x fzfa-find-any
                │
                ▼
  fzfa-find-any
    → fzfa-multi-read
          fzfa-find-any-commands

  PHASE 1: EXTRACT  (loop over all commands)
    let multi-mode = :extract
    catch 'fzfa-extracted (funcall cmd)
      ; inside cmd, completing-read entry sees :extract → throw args
    builds source plist:
      (:name "buffer"
       :items names
       :category fzfa-buffer
       :annotate <derived from category>
       :action  λ(c). re-run cmd with (:inject . c))   ; closes over cmd

  PHASE 2: MULTI UI
    fzfa--multi-read merges all sources, user picks CAND
    looks up source via fzfa-src-idx text-prop, calls :action

  PHASE 3: INJECT  (one cmd is replayed)
    let multi-mode = (:inject . CAND)
    (funcall fzfa-buffer)
      ; inside cmd, completing-read entry returns CAND
    when-let* binds → post-action runs
#+end_src

The cost: each command runs twice per multi session.  Setup work
(=fzfa-hungry-find='s buffer-list walk, etc.) repeats.
Microseconds in practice.

** Mode encoding asymmetry

=fzfa--multi-mode= is the bare symbol =:extract= for extract (no
payload), or the cons =(:inject . CAND)= for inject (carries the
candidate).  Hence the dispatch:

#+begin_src emacs-lisp
  (cond
   ((eq fzfa--multi-mode :extract) ...)        ; bare symbol
   ((eq (car-safe fzfa--multi-mode) :inject)   ; cons head
    ... (cdr fzfa--multi-mode) ...))           ; cons tail = CAND
#+end_src

** Edge cases

- *Commands with =read-*= in body* (e.g. =fzfa-shell-command=
  prompts before reaching the completing-read call): unsupported as
  multi sources — extract would prompt the user.
- *Commands that =user-error= before the completing-read call* (e.g.
  =fzfa-hungry-find= when no file-visiting buffers exist): the
  =catch= returns =nil= or the =user-error= propagates; the source is
  silently skipped.
- *Marginalia annotations*: the multi category is =fzfa-multi= (not
  the per-command category), so per-category marginalia registrations
  don't apply.  =fzfa-multi-read= synthesizes a fallback
  =:annotate= from the extracted =:category= (=buffer= →
  =marginalia-annotate-buffer=, =file= → =marginalia-annotate-file=).

* Custom completion style

The completion framework wants to filter, score, and re-sort the
candidates the collection lambda returns. We don't want any of that —
fzf has already scored, the order is already correct, and applying
=fussy-default-regex-fn= (the typical user style) over the raw query
mangles fzf syntax. So we register a passthrough:

| Function                       | Behavior                                                |
|--------------------------------+---------------------------------------------------------|
| =fzfa-try-completion=     | Returns =(cons string (length string))= — no prefix expansion |
| =fzfa-all-completions=    | Calls =(funcall table string pred t)= — raw passthrough, no PCM or fussy re-filtering. Candidates arrive pre-scored and pre-highlighted from the C module. |
| =fzfa-setup= (autoload)   | Registers the style and pins it for the =fzfa= and =fzfa-file= categories via =completion-category-overrides= |

The collection lambda's metadata returns =(category . fzfa)= (or
=fzfa-file=) plus =(display-sort-function . identity)= and
=(cycle-sort-function . identity)= so vertico/icomplete don't re-sort.

The category was deliberately named =fzfa= (not =fzf=) to avoid
colliding with any user config that already maps =fzf= to fussy.

The =fzfa-file= category exists so =marginalia-annotate-file= can
attach to file commands (=fzfa-find=, =fzfa-fd=, etc.)
without the marginalia → file-category override pulling them back
into fussy's filtering. See History → "Marginalia interaction is
broken" in =project.org= for the full diagnosis.

* C-side match highlighting

Matched characters are highlighted inside =fzf_native_async_candidates=
before strings reach the Elisp layer, so no Elisp regex pass is needed.

The old approach — =completion-pcm--hilit-commonality= called from
=fzfa-all-completions= — built a PCM pattern with one =any= token per
query character, which Emacs compiled to a regex with N nested =.*= groups.
This caused exponential backtracking on non-matching candidates. For a 32-
character query with 1038 candidates the hang was 18 seconds.

The current approach:

1. In =fzf_native_async_candidates=, after dispatching the scoring job, the
   C code reads =fzfa-highlight= via =symbol-value=:
   - =nil= → skip highlighting.
   - =t= → highlight all returned candidates (=hl_cap = rcount=).
   - Integer N → highlight the top N candidates (=hl_cap = N=).
2. Parse =filter_for_hilit= into an =fzf_pattern_t= (one shared pattern for
   the whole highlight pass).
3. For each =snap[0..hl_cap-1]= (highest-scoring candidates, prepended last
   so they land at the front of the returned list):
   - =fzf_get_positions(str, pattern, slab)= → =pos->data[]= in descending
     byte-offset order.
   - Iterate ascending, merge adjacent offsets into runs, call
     =put-text-property= once per run with =face=completions-common-part=.
4. Free pattern and slab before returning.

The Emacs string object already has the face applied when it is consed into
the result list. Frontends (vertico, icomplete) display it without any
further Elisp highlighting work.

*Byte vs. character positions:* =fzf_get_positions= returns byte offsets;
=put-text-property= uses character positions. For ASCII candidates (the
common case) these are identical. Multi-byte UTF-8 candidates may have
slightly misaligned face ranges — acceptable and consistent with the
limitation in fussy's fzf-based highlighting.

* Frontend abstraction

Two helpers route around vertico/icomplete/ivy differences:

| Function                       | Purpose                                                   |
|--------------------------------+-----------------------------------------------------------|
| =fzfa--frontend-index=    | Current selection index for the active frontend, or =nil= |
| =fzfa--frontend-exhibit=  | Trigger the frontend to re-read the completion table     |

ivy uses a *push* model rather than pull, so it has its own dedicated
path: a closure pushes via =ivy--set-candidates= then redraws via
=ivy--exhibit=. ivy bypasses =completion-styles= entirely.

* Timer model (async path only)

Two timers, two purposes:

| Timer                                         | Period | Purpose                                                     |
|-----------------------------------------------+--------+-------------------------------------------------------------|
| =fzfa-refresh-delay= (regular timer)     | 0.05s  | Polls =:snapshot-generation= through metadata-only status. On change, *schedules an idle timer* (=run-with-idle-timer 0 nil=) to call =fzfa--frontend-exhibit=. Throttled by =fzfa-input-throttle=. |
| =fzfa-input-debounce= (idle timer)       | 0.1s   | Self-healing: if a previous tick's exhibit was interrupted by =while-no-input=, this re-tries it after the user pauses typing.    |

The double-indirection — regular timer detects, idle timer exhibits —
is deliberate. Regular timer ticks count as pending input from the
=while-no-input= perspective; calling =vertico--exhibit= directly from
a regular timer can interrupt status or snapshot materialization.  Native
scoring continues independently.  Idle timers fire between events.

=fzfa-input-throttle= (default 0.2s) caps how often the regular
timer will actually schedule an exhibit. Streaming new candidates at
60 Hz otherwise floods the UI.

* Prompt overlay

Format: =dir » idx/[sent](total) =

| Field   | Source                                                      |
|---------+-------------------------------------------------------------|
| =dir=   | =(abbreviate-file-name default-directory)=                  |
| =idx=   | =fzfa--frontend-index= (1-based; omitted on icomplete) |
| =sent=  | =min(filtered, fzfa-max-candidates)=                   |
| =total= | Atomic status/snapshot metadata for the owned request. |

Updated via =post-command-hook= so =idx= tracks live during
navigation. =fzfa-max-candidates= (default 10 000) caps =sent= so
the cost of building the Emacs list stays bounded; =filtered= and
=total= always report ground truth so the user is never misled.

* Frontend count format suppression

Bound via =minibuffer-with-setup-hook= + =setq-local= (not =let=,
which doesn't reach the minibuffer buffer):

| Frontend  | Variable                   | Set to |
|-----------+----------------------------+--------|
| vertico   | =vertico-count-format=     | =nil=  |
| icomplete | =icomplete-matches-format= | =nil=  |
| ivy       | =ivy-count-format=         | =""=   |

This stops each frontend's built-in =1/2000= counter from doubling up
with our overlay.

* Empty-query and timer-triggered empty-string handling

The completion table receives =str=""= in two distinct situations:
genuine empty query (user has cleared the minibuffer) and timer
re-exhibit when no minibuffer window is active. The lambda
distinguishes:

#+begin_src elisp
  (if (not (string-empty-p str))
      str                        ; genuine query
    (when-let* ((win (active-minibuffer-window)))
      (with-current-buffer (window-buffer win)
        (minibuffer-contents))))  ; refresh — read live minibuffer
#+end_src

If neither path produces a query, return the cached =last-result=
unchanged. This prevents an empty-query call from poisoning the cache
mid-typing.

* Behavior reference (canonical input → output, Elisp side)

** Empty query (async path)

| Input                                          | Output                                                     |
|------------------------------------------------+------------------------------------------------------------|
| Active minibuffer, =str=""=                    | Unfiltered =score_results= snapshot from the C module, capped at =fzfa-max-candidates=. |
| No active minibuffer, =str=""=                 | Cached =last-result= unchanged (timer re-exhibit case).    |

** Empty query (sync path)

| Input                              | Output                                                |
|------------------------------------+-------------------------------------------------------|
| =candidates=, =str=""=             | =candidates= returned unchanged (the lambda's identity branch). |

** Generation change

| Event                                      | Effect                                                  |
|--------------------------------------------+---------------------------------------------------------|
| Owned request's =:snapshot-generation= changes | 50 ms regular timer detects → schedules idle-timer exhibit (subject to =fzfa-input-throttle=). |
| Idle-timer exhibit fires                       | =fzfa--frontend-exhibit= calls into the active frontend; the completion table polls status and materializes only a new authoritative snapshot. |

** Quit (=C-g= / ESC)

| Event                                      | Effect                                                |
|--------------------------------------------+-------------------------------------------------------|
| User aborts =completing-read=              | =unwind-protect= runs: cancel timers, remove overlay, and =fzf-native-async-stop= each handle. Session-owned producer/reader/coordinator state and arena are destroyed; the process-wide native worker pool remains reusable. |

* Concurrency model — quick reference (Elisp side)

| Invariant                                                 | Why it holds                          |
|-----------------------------------------------------------+---------------------------------------|
| Idle-timer exhibits don't trip =while-no-input= around status/snapshot calls. | Idle timers don't count as pending input; regular timers do, which is why exhibits are *scheduled* by a regular timer but *fired* by an idle one. |
| Stable redraw neither resubmits nor rematerializes.       | =fzfa-source= owns the full request key, native request ID, snapshot generation, and cached Elisp output. |
| The Elisp side never blocks on the C scoring thread.      | Submit and status are non-blocking; snapshot copies only an already-published result and can be interrupted by pending input. |
| Marginalia annotators don't pull candidates into a different completion style. | =fzfa-file= category routes file annotations through marginalia *and* keeps the completion style as =fzfa=. |
